# BUG-UI-001 — открытая карточка сохраняет SUBMITTED после завершения проверки

**Build:** 0.1.0, исходный commit `4c61ef1`. **Environment:** GitHub Actions Ubuntu, Docker, Chromium; локально Windows/Chromium с контролируемым порядком ответов. **Seed:** 42, tenant A.

**Severity:** Medium. **Priority:** P2. **Status:** fixed; результат повторной проверки указан ниже. **Requirement:** FR-UI-02, FR-UI-05. **Test case:** TC-031.

## Проблема и влияние

После успешной отправки открытая карточка может показывать `SUBMITTED` / «Отправлено», хотя локальная проверка уже завершилась и сервер возвращает `UNDER_REVIEW`. Пользователь не видит актуальный шаг без ручного обновления или повторного открытия. Бизнес-состояние БД не откатывается; дефект относится к синхронизации UI.

## Предусловия и шаги

1. Войти как `applicant.a`; создать заявление и загрузить синтетический PDF.
2. Подготовить документ и подписать; дождаться доступной команды отправки.
3. Отправить заявление и оставить карточку открытой.
4. Первый GET карточки после 202 успевает прочитать законный снимок `SUBMITTED`, до завершения background task.
5. Система переходит в `UNDER_REVIEW`. Сравнить статус в открытой карточке и в новом GET/очереди.

**Expected:** карточка автоматически получает актуальное состояние, audit и результат проверки. **Actual:** остаётся «Отправлено», v5; существующий E2E прекращается по истечении ожидания `UNDER_REVIEW`.

## Evidence и воспроизводимость

- [Первый реальный CI-прогон](https://github.com/topchik77/adlabs-govflow-qa/actions/runs/38739137150): PostgreSQL regression прошёл, UI E2E упал на ожидании статуса.
- Сообщение: `Expected substring: "На рассмотрении"; Received: "Отправленоv5 · документ rev 2"`.
- [JUnit детерминированного воспроизведения до исправления](../../reports/bug-ui-001-before.xml): 1 test, 1 failure.
- [Регрессионный тест](../../frontend/demo-portal/e2e/reference.spec.ts) управляет первым GET-снимком после реального submit. Возвращается допустимый accepted snapshot того же заявления, затем следующие GET читают настоящее API. Это воспроизводит порядок событий без фиксированного sleep и не меняет серверные данные.

Первоначально дефект зависит от тайминга. В детерминированной проверке старая frontend-сборка воспроизводит его стабильно.

## Причина

Список и открытая карточка хранят разные snapshots. Polling зависел только от `items`: если список уже получил UNDER_REVIEW, таймер прекращался. Состояние `selected` оставалось SUBMITTED и не обновлялось автоматически.

## Исправление

Карточка независимо обновляет свой snapshot, audit и integrations, пока находится в SUBMITTED/VALIDATING. Таймер отменяется при закрытии карточки, смене пользователя/сессии или выходе из технической стадии. Ответ старого запроса не применяется после cleanup.

## Проверка исправления

Тот же E2E обязан сначала увидеть «Отправлено», затем автоматически «На рассмотрении» и завершить процесс через reviewer/officer с двумя подписями и 10 audit events. Итоговый [Playwright JUnit](../../reports/playwright.xml) хранит результат повторного прогона.

**Workaround до исправления:** ручное обновление карточки. **Lifecycle:** detected in CI → reproduced with controlled ordering → diagnosed → fixed → regression retest.
